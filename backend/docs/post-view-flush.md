# 조회수 증가분 DB 배치 저장 — #754

## 저장 흐름

1. 서버 시작 10분 후 첫 저장을 실행한다. 이후에는 이전 실행이 끝난 시점부터 10분 후 다시 실행한다.
2. `PostViewStore.prepareFlushBatches()`로 게시글별 증가분을 가져온다. 미확정 배치가 있으면 기존 배치 ID와 증가분을 그대로 재사용한다.
3. `PostViewFlushWriter.writeAll()`이 이번 실행에서 준비한 전체 목록을 하나의 `REQUIRES_NEW` 트랜잭션으로 저장한다. 각 누계를 `view_count + delta`로 갱신하며 별도 반영 이력은 기록하지 않는다. 반환값과 삭제 글 제외 결과는 없다.
4. 전체 트랜잭션 커밋 후 각 Counter의 `completeFlush()`로 메모리 배치를 완료한다. DB I/O 중에는 Counter의 락을 잡지 않는다.

100개 단위 분할이나 JDBC 배치는 사용하지 않는다. 한 게시글의 UPDATE가 실패하면 전체 트랜잭션을 롤백한다. 저장 중 발생한 새 조회는 `pendingDelta`에 남아 다음 배치에 포함된다. 상세 조회의 `confirmedCount + pendingDelta + inFlightBatch.delta()` 계산은 유지한다.

`PostViewFlushService`는 `AtomicBoolean.compareAndSet()`으로 배치 준비·DB 저장·메모리 완료 전체 구간의 실행 겹침을 막는다. 실행 중 들어온 후속 호출은 기다리지 않고 건너뛰며, 성공·실패 여부와 관계없이 실행 가드를 해제한다.

## 소프트 삭제

삭제 전에 이미 인정한 조회 증가분은 게시글이 이후 소프트 삭제되어도 저장한다. 소프트 삭제는 게시글과 조회수 누계 행을 보존하며, 코로그 게시글 일괄 삭제에도 같은 정책을 적용한다. 조회수 UPDATE는 게시글 삭제 상태에 대한 `EXISTS` 조건이나 상태 분류용 추가 SELECT를 사용하지 않는다.

삭제된 게시글의 새 조회 등록 POST는 기존 서비스 검증에서 계속 거절한다. 이미 생성한 Counter는 삭제나 저장 완료를 이유로 제거하지 않으며, 기존처럼 별도 만료 없이 유지한다. 이 정책의 근거는 [ADR 0014](../../docs/adr/0014-post-view-flush-retry.md)에 기록한다.

## 실패와 재시도

UPDATE가 0건이면 누계 행 부재나 값의 범위 초과 등 누계가 유효하지 않은 상태로 처리한다. 게시글의 삭제 여부를 확인해 정상 제외하지 않는다. 어느 한 배치라도 실패하면 앞서 실행한 UPDATE까지 전체 롤백하고 모든 미완료 배치를 메모리에 유지한다.

저장 실패 또는 메모리 완료 처리 실패 시 미완료 배치를 유지하고 **다음 정기 실행에서 재시도**한다. 즉시 반복 재시도하지 않는다. 재시도는 기존 `inFlightBatch`를 그대로 사용하며 그동안의 새 조회를 합치지 않는다. 커밋 실패의 경우 writer 프록시가 예외를 반환하므로 메모리 배치를 완료하지 않는다.

중복 반영 방지 이력은 사용하지 않는다. DB는 커밋했지만 연결 단절 등으로 성공 여부를 확인하지 못하거나 커밋 후 메모리 완료에 실패하면, 다음 실행에서 같은 배치가 다시 더해질 수 있다. 참고용 조회수 지표에 발생하는 과대 집계와 DB 누계가 메모리 합계보다 커지는 차이를 허용한다. 기존 V4 마이그레이션과 사용하지 않는 `post_view_flush_batch` 테이블은 보존한다.

## 설정

| 환경 변수 | 기본값 | 의미 |
| --- | --- | --- |
| `POST_VIEW_FLUSH_ENABLED` | `true` | 자동 배치 저장 활성화 |
| `POST_VIEW_FLUSH_INTERVAL` | `10m` | 최초 대기 시간과 실행 완료 후 대기 시간 |
| `POST_VIEW_REGISTRATION_ENABLED` | `false` | 기존 조회 등록 API 활성화 |

저장 주기는 1밀리초 이상의 Duration이어야 하며, 예를 들어 `1h`로 바꿀 수 있다. H2·MySQL 테스트 프로필에서는 자동 저장을 꺼서 테스트 도중 DB 상태가 바뀌지 않게 한다. `dev` 프로필의 조회 등록 기본값은 `true`이며, `POST_VIEW_REGISTRATION_ENABLED=false`로 끌 수 있다. 공통 설정과 운영 프로필의 기본값은 `false`다.

## 한계와 검증 범위

단일 활성 JVM 전제를 유지한다. 실행 겹침 방지도 같은 JVM 안에서만 유효하다. 저장 전 증가분·방문 기록은 메모리에 있으므로 비정상 종료 시 유실될 수 있다. 정상 종료 시 강제 저장도 이번 범위에 포함하지 않는다. 10분은 실행 간 대기 시간이며 DB 장애나 저장 소요 시간을 포함한 최대 저장 지연 보장은 아니다. 한 누계의 오류가 지속되면 전체 목록의 저장도 계속 실패할 수 있다.

`PostViewFlushWriterIntegrationTest`는 반영 이력 없는 실제 저장과 누계 누락·범위 초과 시 실패를 검증한다. `PostViewFlushIntegrationTest`는 실제 Counter·DB로 전체 롤백과 다음 실행 재시도, 커밋 후 메모리 완료 실패에 따른 중복 증가, 소프트 삭제 후 기존 증가분 저장, 실행 겹침 방지와 저장 중 새 조회 보존을 검증한다. `PostViewFlushSchedulerTest`는 기본 10분·설정 변경·비활성화와 잘못된 주기 거절을 검증한다.

기존 성능 실험은 게시글별 트랜잭션 기준이며, 전체 목록 저장의 성능 측정과 주기 비교 실험은 별도 작업이다. 기존 등록 POST·상세 공개 권한·피드 응답 계약은 바뀌지 않는다.
