# 조회수 증가분 DB 배치 저장 — #754

## 저장 흐름

1. 서버 시작 10분 후 첫 저장을 실행한다. 이후에는 이전 실행이 끝난 시점부터 10분 후 다시 실행한다.
2. `PostViewStore.prepareFlushBatches()`로 게시글별 증가분을 가져온다. 미확정 배치가 있으면 기존 배치 ID와 증가분을 그대로 재사용한다.
3. `PostViewFlushWriter`가 게시글 배치마다 독립된 트랜잭션에서 반영 이력을 INSERT하고 누계를 `view_count + delta`로 갱신한다.
4. 트랜잭션 커밋 후 `completeFlush()`로 메모리 배치를 완료한다. DB I/O 중에는 Counter의 락을 잡지 않는다.

스케줄러와 순회 서비스는 전체 배치를 하나의 트랜잭션으로 묶지 않는다. 한 게시글의 실패는 로그에 남기고 다음 게시글을 처리한다. 저장 중 발생한 새 조회는 `pendingDelta`에 남아 다음 배치에 포함된다. 상세 조회의 `confirmedCount + pendingDelta + inFlightBatch.delta()` 계산은 유지한다.

## 실패와 재시도

기존 V4의 `post_view_flush_batch.batch_id` PK를 중복 반영 방지에 사용한다. 같은 ID로 이미 저장된 게시글·증가분이 일치하면 다시 더하지 않는다. 같은 ID에 다른 내용이 들어오면 오류로 처리한다. `created_at`은 UTC로 저장하는 메타데이터이며, DB 시간 정밀도 차이 때문에 재시도 내용 비교에는 사용하지 않는다.

배치 이력과 누계 UPDATE는 함께 커밋하거나 롤백한다. UPDATE가 허용 범위를 벗어나거나 대상이 없어 실패하면 이력만 남기지 않는다. 같은 배치의 최초 INSERT가 동시에 실행되어 PK 충돌이 나면 충돌한 트랜잭션은 롤백한다.

저장 실패 또는 메모리 완료 처리 실패 시 배치를 유지하고 **다음 정기 실행에서 재시도**한다. 즉시 반복 재시도하지 않는다. DB는 커밋했지만 연결 단절 등으로 성공 여부를 확인하지 못해도, 다음 실행에서 기존 이력을 확인해 증가분을 중복 반영하지 않는다. 커밋 실패의 경우 writer 프록시가 예외를 반환하므로 메모리 배치를 완료하지 않는다.

## 설정

| 환경 변수 | 기본값 | 의미 |
| --- | --- | --- |
| `POST_VIEW_FLUSH_ENABLED` | `true` | 자동 배치 저장 활성화 |
| `POST_VIEW_FLUSH_INTERVAL` | `10m` | 최초 대기 시간과 실행 완료 후 대기 시간 |
| `POST_VIEW_REGISTRATION_ENABLED` | `false` | 기존 조회 등록 API 활성화 |

저장 주기는 1밀리초 이상의 Duration이어야 하며, 예를 들어 `1h`로 바꿀 수 있다. H2·MySQL 테스트 프로필에서는 자동 저장을 꺼서 테스트 도중 DB 상태가 바뀌지 않게 한다. 조회 등록 기본값은 계속 비활성이며 이번 변경으로 운영 집계를 켜지 않는다.

## 한계와 검증 범위

단일 활성 JVM 전제를 유지한다. 저장 전 증가분·방문 기록은 메모리에 있으므로 비정상 종료 시 유실될 수 있다. 정상 종료 시 강제 저장도 이번 범위에 포함하지 않는다. 10분은 실행 간 대기 시간이며 DB 장애나 저장 소요 시간을 포함한 최대 저장 지연 보장은 아니다. 배치 이력의 자동 삭제는 구현하지 않는다.

`PostViewFlushWriterIntegrationTest`는 실제 저장, 동일 배치 재전달·동시 전달의 중복 방지, 내용 충돌과 부분 저장 롤백을 검증한다. `PostViewFlushIntegrationTest`는 실제 Counter·DB로 실패 후 다음 실행 재시도, 게시글별 실패 격리, 커밋 후 메모리 완료와 저장 중 새 조회 보존을 검증한다. `PostViewFlushSchedulerTest`는 기본 10분·설정 변경·비활성화와 잘못된 주기 거절을 검증한다.

성능 측정과 주기 비교 실험은 별도 작업이다. 기존 등록 POST·상세 공개 권한·피드 응답 계약은 바뀌지 않는다.
