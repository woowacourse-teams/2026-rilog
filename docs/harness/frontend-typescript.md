# 프론트엔드 TypeScript 사용 기준

규칙의 적용 범위는 [frontend/AGENTS.md](../../frontend/AGENTS.md)에서 정한다. 이 문서는 선택 이유, 예외와 확인 방법을 기록한다. API 응답의 런타임 검증 결정은 [ADR 0005](../adr/0005-frontend-runtime-validation.md)를 따른다.

## 컴파일 타임과 런타임

TypeScript의 타입은 컴파일 후 사라진다. `strict`와 `tsc --noEmit`은 소스 코드 안의 타입 관계를 검사하지만 서버 응답, URL, storage, 환경변수의 실제 값을 검사하지 않는다. `response.json<T>()`, `as T`, `satisfies`도 실행 중에 `T`를 확인하지 않는다. 외부 값을 믿을 수 있는 구간은 해당 값의 구조를 런타임에서 검사한 **이후**부터다. 검증하지 않는 값은 팀이 관리하는 API 계약에 의존하는 것으로 보고, 그 위험을 아래 경계 목록에 남긴다.

## 선언과 이벤트

| 기준                                              | 성격           | 이유와 예외                                                                                                                                                                                                               | 강제 수단                                 |
| ------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Props와 이름 있는 객체 계약은 `interface`         | 팀 스타일 선택 | 객체의 확장·구현 형태가 읽기 쉽다. union, tuple, 함수, primitive alias, mapped/conditional type에는 `type`을 쓴다. 객체 alias가 필요한 예외는 이슈나 PR에 이유를 적는다. 이 선택만으로 런타임 안전성이 높아지지는 않는다. | `consistent-type-definitions`, 리뷰       |
| 타입만 참조하는 import는 `import type`            | 정적 코드 기준 | 런타임 의존성과 타입 의존성을 구분한다.                                                                                                                                                                                   | `consistent-type-imports`                 |
| JSX 인라인 이벤트는 추론에 맡긴다                 | 정적 코드 기준 | 중복 타입 표기를 줄인다. 함수로 분리하면 `FormEvent<HTMLFormElement>` 또는 해당 React 이벤트/핸들러 타입을 명시한다. DOM `Event`로 단정하지 않는다.                                                                       | 타입 검사, 리뷰                           |
| 비동기 이벤트는 실패 처리 책임을 정한다           | 동작 안전성    | Promise를 반환하는 핸들러의 오류를 누락하면 사용자 피드백과 관측이 빠진다. `void` 표기만으로 오류가 처리되지는 않는다.                                                                                                    | 기존 Promise 린트, 실패 흐름 테스트, 리뷰 |
| null 가능성을 분기해서 좁힌다                     | 정적 안전성    | `!`는 실제 null을 막지 못한다. `*.unit.test.*`, `*.component.test.*`, `*.spec.ts`의 fixture·DOM 단언에만 린트 예외를 둔다. 다른 브라우저 fixture는 null을 확인한다.                                                       | 운영 코드 `no-non-null-assertion`         |
| 판별 가능한 union의 `switch`는 모든 경우를 다룬다 | 정적 안전성    | 새 variant가 추가될 때 누락된 처리를 발견한다. 기본 분기는 현재 case의 누락을 가리지 않아야 한다.                                                                                                                         | `switch-exhaustiveness-check`             |
| 타입 단언은 검증의 대체물이 아니다                | 런타임 안전성  | 라이브러리 경계 등 타입만으로 표현할 수 없는 경우에 한정하고 근거를 남긴다. 외부 JSON을 DTO로 단언하지 않는다.                                                                                                            | 기존 unsafe 린트, 리뷰                    |

`noUncheckedIndexedAccess`와 `exactOptionalPropertyTypes`는 이번 변경에서 활성화하지 않는다. 현재 인덱스 접근과 optional 계약 전반을 바꾸는 별도 마이그레이션이 필요하며, 두 옵션 모두 외부 JSON 검증을 대신하지 않는다.

## 런타임 경계

선택한 endpoint는 성공 응답의 JSON 문법과 필수 구조 전체를 raw API 함수에서 검사한다. 기존 optional·null 계약을 유지하고 추가 필드는 허용한다. 검증 함수는 resource별 기존 API 모듈에 두며, 새 범용 schema 계층을 만들지 않는다. JSON 문법 오류와 구조 오류는 모두 응답 확인 실패로 처리하고 응답 본문이나 파싱 오류 원문을 기록하지 않는다.

| 입력                                                        | 이번 적용                                                                             | 실패 처리                                                                                         |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| OAuth callback·토큰 갱신·onboarding의 인증 값, 내 정보 응답 | 응답 구조와 상태 enum, Bearer 토큰 형식을 검사한다.                                   | 잘못된 값으로 세션·가입 완료를 확정하지 않는다.                                                   |
| 게시글·초안 상세                                            | 메타데이터와 BlockNote 본문의 활성 스키마를 검사한다. 빈 배열은 정상 문서로 허용한다. | `null`·손상된 본문은 로드 오류로 처리하고 빈 편집기에 채우지 않는다.                              |
| 게시글·초안 저장, 수정, 발행 응답                           | 후속 이동과 캐시 갱신에 쓰는 식별자를 포함한 DTO를 검사한다.                          | 성공 후처리를 막고 작성 내용을 보존한다. 서버에 이미 저장됐을 수 있으므로 자동 재전송하지 않는다. |
| 인라인 댓글 본문·사이드바 조회와 작성·수정·삭제 응답        | 중첩 그룹·작성자·권한·상태와 쓰기 결과의 필수 DTO를 검사한다.                         | 손상된 조회 응답은 캐시에 넣지 않는다. 쓰기 결과가 불확실하면 초안을 보존하고 목록을 갱신한다.    |
| 업로드용 presign 응답                                       | URL, headers와 나머지 필수 필드를 검사한다.                                           | 잘못된 응답으로 파일 PUT을 시작하지 않는다.                                                       |
| API 오류 응답                                               | `invalidParams`의 배열 원소까지 검사한다.                                             | 불완전한 필드 오류는 기존 일반 HTTP 오류로 처리한다.                                              |
| 로그인 후 이동 경로                                         | 저장된 redirect가 앱 내부 경로인지 확인한다.                                          | 외부 URL·실행 스킴은 기본 경로 `/`로 돌린다.                                                      |
| URL의 ID·필터·enum, 분석용 storage                          | 기존 가드를 재사용하고 JSON parse 결과를 `unknown`에서 좁힌다.                        | 기존 유효하지 않은 값 처리를 유지한다.                                                            |

### 이번 범위에서 검증하지 않는 값

아래 항목은 `apiClient`의 JSON 파싱과 TypeScript 타입을 사용하지만 DTO 구조는 확인하지 않는다. HTTP 오류 처리와 화면별 방어는 일부 실패만 막는다. 검증 대상 전환 조건이 생기면 해당 endpoint의 raw API 함수에서 가드와 실패 정책을 함께 추가한다.

| 입력                                 | 소비 위치와 현재 방어                                                                                             | 수용한 위험과 전환 조건                                                                                                                                                           |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 일반 피드·블로그 공개 글·코로그 조회 | 피드·블로그 목록 mapper와 query가 일부 필수 값을 확인하고 실패 UI를 제공한다.                                     | 손상된 항목이 빠지거나 잘못 표시될 수 있다. 인증·편집·쓰기 후처리에 값을 사용하거나 계약 불일치가 관측되면 해당 조회 응답을 검증한다.                                             |
| 내 초안 목록                         | 글쓰기 초안 목록 query에서 페이지와 `hasNext`를 사용한다. 요청 실패 시 목록 오류 UI를 사용한다.                   | 잘못된 성공 응답은 pagination이나 목록을 왜곡할 수 있다. 손상 응답이 관측되거나 초안 복원 판단에 목록 값이 쓰이면 검증한다. 초안 **상세**는 이미 검증한다.                        |
| 코로그 생성·멤버 초대                | 생성 폼은 응답 `data`의 존재와 입력 유효성을 확인하고, mutation 오류를 표시한다. 초대도 mutation 오류를 표시한다. | 필드 타입이 틀린 성공 응답으로 잘못 이동하거나 성공 처리할 수 있다. 오류가 관측되거나 인증·권한·재시도 정책이 이 응답에 의존하면 쓰기 응답 검증과 결과 확인 실패 처리를 추가한다. |
| 챕터 생성·이름 변경                  | 공유 mutation과 관리 UI에서 입력·오류 코드를 처리한다.                                                            | 필드 타입이 틀린 성공 응답을 정상 완료로 처리할 수 있다. 후속 이동·권한 판단에 쓰이거나 계약 불일치가 관측되면 검증한다.                                                          |
| `NEXT_PUBLIC_*` 환경변수             | `.env.example`과 CI 환경값으로 실행 환경을 설정한다. API 클라이언트는 지정된 base URL을 사용한다.                 | 로컬 누락·오설정 시 요청이 잘못된 서버로 갈 수 있다. 환경별 장애가 반복되거나 배포 진입 전 필수 조건이 되면 시작 시 별도 검증을 검토한다.                                         |

JWT의 진위와 최종 권한 판단은 서버가 맡는다.

API나 DTO를 수정할 때는 다음을 함께 확인한다.

1. 입력이 위 검증 경계에 속하는지, 실패 시 기존 상태를 안전하게 유지하는지 확인한다.
2. DTO, 런타임 가드와 정상·손상 응답 fixture를 함께 갱신한다. `as`나 `.json<T>()`로 가드를 우회하지 않는다.
3. BlockNote 스키마 또는 버전을 변경하면 본문 decoder와 저장 문서 호환성 fixture를 함께 검토한다.
4. 검증 예외가 필요하면 이유와 사용 구간을 리뷰에 남긴다. 실행하지 못한 검증도 보고한다.

## 빌드와 병합 확인

`pnpm check`는 `format:check → lint → next typegen + tsc --noEmit → unit → component → next build` 순서다. TypeScript 검사는 build 전에 독립적으로 실행되고, Next.js build에서도 production 빌드 계약을 확인한다. `pnpm test:e2e:prod`는 build 결과를 사용해 별도로 실행한다. LLM 작업 지침과 리뷰는 판단을 돕지만 결정적인 위반 검출은 컴파일러·린트·테스트가 담당한다.

품질 workflow는 `develop`·`production` 대상 모든 PR에서 실행된다. frontend와 품질 workflow 파일이 바뀌지 않은 PR은 `Frontend Quality` job의 무거운 검증 단계를 건너뛴다. 이 job은 두 브랜치의 required check다. 자세한 실행 환경과 유지·변경 조건은 [품질 게이트](quality-gates.md)를 따른다.
