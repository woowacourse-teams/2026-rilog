# ADR 0014: 조회수 전체 배치의 단일 트랜잭션 저장과 정기 재시도

- 상태: 승인
- 날짜: 2026-10-19
- 소유자: Backend

## 맥락

조회수 증가분을 저장하지 못하면 폐기하던 정책을 변경한다. 커밋 횟수를 줄이기 위해 이번 실행에서 준비한 전체 배치를 한 트랜잭션으로 저장하고, 실패한 증가분은 메모리에 유지한다. 조회수는 참고용 지표이므로 커밋 확인 실패나 메모리 완료 실패 후 재시도로 발생할 수 있는 과대 집계를 허용한다. 이 결정은 ADR 0013을 대체한다.

## 결정

- `PostViewFlushWriter.writeAll()`이 전체 목록의 UPDATE를 하나의 독립 트랜잭션으로 수행한다. 100개 단위 분할과 JDBC 배치는 도입하지 않는다.
- 커밋 성공 후에만 각 Counter의 `completeFlush()`를 호출한다. 저장이 실패하면 전체 트랜잭션을 롤백하고 미완료 배치를 유지한다.
- `prepareFlush()`는 기존 `inFlightBatch`를 그대로 반환한다. 새 조회는 `pendingDelta`에 따로 모으며 재시도 중인 배치에 합치지 않는다. `discardFlush()`는 제거한다.
- 스케줄러는 기존처럼 이전 실행 완료 후 10분을 기다린다. 실패 직후 즉시 재시도하지 않는다.
- `FlushService`의 `AtomicBoolean`으로 준비·DB 저장·메모리 완료 전체 구간의 실행 겹침을 방지한다. 이미 실행 중이면 후속 호출은 기다리지 않고 건너뛴다. 종료 시 성공·실패 여부와 관계없이 가드를 해제한다.
- 삭제된 게시글은 UPDATE의 `EXISTS` 조건에서 제외한다. UPDATE 0건이면 게시글의 삭제·부재를 확인해 정상 제외하고, 활성 게시글의 누계 누락·범위 초과는 저장 실패로 처리한다.
- 삭제·부재가 확인된 Counter는 전체 트랜잭션 커밋 후 제거한다. 코로그 게시글 일괄 삭제도 같은 DB 조건으로 처리한다. 기존 DB 조회수 행은 소프트 삭제 정책에 따라 보존한다.
- 중복 반영 방지 이력은 다시 도입하지 않는다. 같은 배치가 재전달되면 다시 UPDATE될 수 있다.

## 결과와 후속 작업

- 실패한 트랜잭션의 증가분은 다음 정기 실행에서 다시 저장한다. 애플리케이션 종료 시 메모리 미저장 증가분의 유실은 기존처럼 허용한다.
- 한 게시글 저장 오류로 전체 UPDATE가 롤백된다. 원인이 지속되면 다음 실행도 실패할 수 있다.
- DB 커밋 성공을 확인하지 못하거나 메모리 완료 처리가 실패하면 재시도로 증가분이 중복 반영될 수 있다. DB 누계가 메모리 합계보다 커지는 차이도 허용한다.
- 삭제와 저장의 완전한 직렬화를 위한 Post 행 잠금은 추가하지 않는다. 이미 저장 처리가 진행된 뒤 삭제되는 경우까지 소급 취소하지 않는다.
- 삭제 Counter의 제거 시점은 해당 글이 배치 대상이 되어 삭제·부재가 확인되고 전체 커밋이 완료된 뒤다. 증가분이 없는 Counter의 삭제 즉시 제거는 구현하지 않는다. 새 조회 등록의 삭제 게시글 거절은 기존대로 유지한다.
- Counter 잠금을 잡은 채 DB I/O를 하지 않는다. 실행 겹침 방지는 같은 JVM 안에서만 유효하며, 다중 인스턴스 전환은 별도 설계가 필요하다.
- 기존 V4 마이그레이션과 사용하지 않는 배치 기록 테이블을 보존한다. API·프론트엔드 변경은 없다.
- 이전 성능 실험은 게시글별 트랜잭션 기준이다. 이번 변경의 저장 시간과 긴 트랜잭션 영향은 재측정하지 않았다.
