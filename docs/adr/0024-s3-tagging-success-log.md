# ADR-0024: S3 객체 태깅 성공을 INFO로 기록

- 상태: 제안
- 날짜: 2026-11-01
- 소유자: backend

## 맥락

#622는 객체 수에 비례해 늘어나는 로그의 활용도가 실패 탐지 목적에 비해 낮다고 보고 S3 태깅 성공 로그를 제거했다. 이후 #805가 성공 INFO 로그를 다시 추가했지만 `.log()` 호출이 빠져 실제로는 출력되지 않았고, 무로그 테스트와 문서도 그대로 남았다. `.log()`를 적용하자 코드와 테스트·문서의 정책이 충돌했다.

## 결정

객체별 태깅 성공을 `s3_object_tagging_success` INFO로 기록한다. 필드는 `operation`, `bucket`, `key`, `tagStatus`, `durationMs`이며 local/dev/prod에 동일하게 적용한다.

실패 기록은 바꾸지 않는다. 객체별 SDK 실패는 `s3_object_tagging_failed` ERROR로 한 번 기록하고 다음 객체를 계속 처리한다. `tagIfExists`에서 객체가 없어 건너뛴 대상은 성공도 실패도 기록하지 않는다.

## 이유

태그 전환이 실제로 이루어진 객체와 소요 시간을 S3를 재조회하지 않고 로그에서 확인할 수 있다. 실패 이벤트와 이름이 구분되어 있어 기존 조회와 알람은 영향을 받지 않는다.

## 검토한 대안

- 성공 로그 제거(#622 정책 유지): 변경이 가장 작지만 #805에서 의도한 성공 기록을 포기하게 된다.
- 작업 단위 요약 INFO: 로그양은 줄지만 객체별 결과를 확인할 수 없다.

## 결과와 후속 작업

- 얻는 이점: 객체별 태깅 결과와 소요 시간을 로그로 조회할 수 있다.
- 감수하는 비용/위험: 로그양이 태깅 대상 수에 비례해 늘고, 압축본 태깅이 더해지면 게시 한 건의 로그도 늘어난다. 성공 로그는 그 시점의 호출 결과이므로 현재 태그 상태의 근거로 쓰지 않는다.
- migration/rollback: 로그 호출과 이벤트 상수를 제거하면 되돌릴 수 있다. 데이터 변경은 없다.
- 다시 검토할 조건: CloudWatch 수집 비용이나 조회 잡음이 활용도보다 커질 때
