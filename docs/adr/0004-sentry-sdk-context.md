# ADR 0004: Sentry SDK 이벤트와 요청 문맥 사용

- 상태: 적용
- 날짜: 2026-10-04
- 영향: frontend의 오류 관측 및 사용자 식별 정보
- 대체: ADR 0003의 이벤트 전체 재구성과 operation별 수집 계약. 백엔드 로그 정책은 유지한다.

## 배경

기존 구현은 SDK 이벤트를 허용 목록으로 다시 만들고, 별도 Error 객체·endpoint 등록표·작업별 수집 규칙을 유지했다. 진단에 필요한 원본 스택과 요청 정보가 빠지면 별도 코드로 다시 추가해야 했다. 기능별 API 구현도 Sentry 등록표를 수정해야 했다.

## 결정

SDK의 원본 오류와 자동 진단 정보를 유지한다. 애플리케이션 코드는 `ErrorTracker` 인터페이스를 사용하고, Sentry 호출과 scope 설정은 `SentryErrorTracker` 구현에 모은다. SDK 초기화와 Next.js 계측 진입점은 별도로 둔다. API 최종 실패는 원래 Error를 `captureException`으로 보내고 operation, HTTP 상태, 오류 코드, 요청 ID를 tag로 붙인다. 요청 method/URL과 공개 오류 응답의 코드·메시지·검증 정보는 context로 붙인다. 로그인된 사용자에게는 내부 user ID만 연결하고 로그아웃 시 해제한다. 서버 요청에 브라우저의 사용자 scope를 공유하지 않는다.

전송 직전 필터는 알려진 인증·서명 값, 쿠키, 요청 본문, 이메일을 제거하고 URL의 민감한 query 값을 치환한다. 입력 검증 정보는 필드 이름만 보낸다. 첨부파일은 허용하지 않는다. 필터는 이벤트 구조와 원본 스택을 재구성하지 않는다. 원문 메시지에 임의의 개인정보가 들어갈 수 있으므로 호출부는 사용자 작성 본문을 Error 메시지나 임의 context에 넣지 않는다.

API 보고는 최종 5xx, 429, 통신·타임아웃, 응답 검증 및 예상 밖의 4xx를 수집한다. 확인된 OAuth 취소, 일반적인 권한·부재·충돌, 알려진 입력 검증은 제외한다. 복구된 중간 재시도는 보고하지 않는다. 별도 화면 영향·복구 연결 이벤트 및 요청별 WeakMap 흐름 저장소는 사용하지 않는다.

## 검증 및 한계

실제 SDK transport에서 원본 예외, 요청·응답 context, 내부 사용자 ID, 민감정보 제거를 확인한다. Query·mutation·직접 호출의 최종 실패와 중복 보고를 검증한다. 정규식 기반 마스킹은 임의 문자열의 모든 개인정보를 탐지하지 못한다. 운영에서 이벤트량과 조사에 필요한 정보의 적절성을 확인하고, 구체적 사례가 생길 때 수집 기준을 조정한다.
