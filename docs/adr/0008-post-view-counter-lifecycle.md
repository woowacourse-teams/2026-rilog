# ADR 0008: 게시글 Counter 유지와 만료 독자 기록 정리

- 상태: 승인
- 날짜: 2026-10-05
- 소유자: Backend
- 관련 이슈: #697

## 맥락

Counter를 계속 유지하면서 전체 개수를 10,000개로 제한하면 오랜 운영 후 새로운 게시글의 조회 집계가 거절될 수 있다. 한도 확인과 등록을 함께 보호하기 위한 전역 잠금도 서로 다른 게시글의 최초 요청을 직렬화한다. 최초 변경은 카운터 개수 한도를 제거하면서 사용이 끝난 Counter도 정리하는 방식이었다. 이후 사용자는 Counter 제거 로직을 없애고 구조를 단순화하도록 요청했다.

## 결정

카운터 개수 한도와 전역 등록 잠금을 제거한다. ConcurrentMap.putIfAbsent로 Future를 등록하고 성공한 요청만 초기화하며, 같은 게시글의 요청은 해당 초기화 결과를 공유한다. DB 로딩과 초기화 결과 대기는 Map 연산 밖에서 진행한다.

초기화된 Counter는 JVM이 종료될 때까지 Registry에 유지한다. 정리 스케줄러는 기본 1분 대기 간격으로 게시글당 최대 1,000개 만료 독자 기록만 삭제하고 공유 독자 슬롯을 반환한다. Counter의 누계·미저장 증가분·미확정 배치는 보존한다.

조회 등록 진입점은 Registry.recordView로 통일한다. 조회와 독자 기록 정리는 같은 Counter의 잠금으로 순서를 보장한다. 사용 종료 상태와 Counter 제거 후 재생성·재시도 처리를 제거한다. 초기화 실패 시에는 실패한 Future만 제거해 다음 요청이 재시도할 수 있게 한다. 독자 기록의 전역 한도는 유지한다.

## 이유와 대안

Counter를 유지하면 정리 후에도 기존 누계로 집계를 이어가며 DB 누계 재조회와 객체 수명 경쟁을 줄일 수 있다. 1시간이 지난 독자 기록은 별도로 정리해 전역 기록 슬롯을 재사용한다. 서버 재시작 시 메모리 상태는 해제된다.

사용이 끝난 Counter까지 퇴거하는 대안은 장시간 실행 중의 메모리 누적을 줄이지만 사용 종료 표시와 재생성·재시도 처리가 필요하다. 이번에는 사용자가 요청한 단순한 구조를 선택하고, Counter 퇴거의 필요성은 실제 메모리 사용량을 측정한 뒤 판단한다. 기존 전역 개수 한도를 유지하는 대안은 새로운 게시글의 집계를 지속적으로 거절할 수 있어 선택하지 않았다.

## 결과와 후속 작업

초기화 등록의 전역 잠금을 없애고 만료 독자 기록만 정리한다. HTTP와 FE 계약은 바꾸지 않는다. 기존 post.views.max-counters 설정은 제거하고 post.views.max-viewer-records와 정리 간격 설정을 사용한다.

Counter 메모리는 JVM 실행 중 초기화한 게시글 수에 따라 늘어나며 전체 메모리의 절대 상한은 없다. 만료 독자 기록 정리는 Counter 객체 수를 줄이지 않는다. 실제 배치 writer·저장 스케줄러·종료 저장은 후속 구현이며, 운영 활성화 전 heap, Counter 수 및 저장·정리 지연을 측정한다. 단일 활성 JVM 및 비정상 종료 시 메모리 유실 전제는 유지한다.
