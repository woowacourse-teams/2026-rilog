# ADR 0008: 게시글 Counter 유지와 게시글별 요청 기반 만료 정리

- 상태: 승인
- 날짜: 2026-10-06
- 소유자: Backend
- 관련 이슈: #697

## 맥락

Counter를 계속 유지하면서 전체 개수를 10,000개로 제한하면 오랜 운영 후 새로운 게시글의 조회 집계가 거절될 수 있다. 한도 확인과 등록을 함께 보호하기 위한 전역 잠금도 서로 다른 게시글의 최초 요청을 직렬화한다. 최초 변경은 카운터 개수 한도를 제거하면서 사용이 끝난 Counter도 정리하는 방식이었다. 이후 사용자는 Counter 제거 로직을 없애고 구조를 단순화하도록 요청했다.

독자 기록에도 전역 개수 한도를 두면 한도에 도달한 순간 새 조회를 거절해야 한다. 이 단계에는 운영 heap 측정 전의 임의 한도보다 1시간 중복 제한의 정확성과 요청 경로에서의 점진적 만료 정리를 우선한다.

## 결정

카운터 개수 한도와 전역 등록 잠금을 제거한다. ConcurrentMap.putIfAbsent로 Future를 등록하고 성공한 요청만 초기화하며, 같은 게시글의 요청은 해당 초기화 결과를 공유한다. DB 로딩과 초기화 결과 대기는 Map 연산 밖에서 진행한다.

초기화된 Counter는 JVM이 종료될 때까지 Registry에 유지한다. 독자 기록 개수의 전역 한도와 용량 초과 오류는 두지 않는다. Counter의 누계·미저장 증가분·미확정 배치는 보존한다.

조회 등록 진입점은 Registry.recordView로 통일한다. Registry는 입력 검증과 Counter 초기화를 담당하고 만료 정리를 오케스트레이션하지 않는다. 조회와 독자 기록 정리는 같은 Counter의 ReentrantLock으로 순서를 보장한다. 사용 종료 상태와 Counter 제거 후 재생성·재시도 처리를 제거한다. 초기화 실패 시에는 실패한 Future만 제거해 다음 요청이 재시도할 수 있게 한다.

각 Counter는 인정된 조회마다 (viewer, acceptedTick)을 자신의 PriorityQueue에 보관하고 마지막 인정 tick 순서로 정렬한다. acceptedTick에는 System.nanoTime 값을 기록하며, 만료 여부와 정렬은 tick 차이로 판단한다. 인정된 조회만 Counter 잠금 안에서 큐 항목을 추가한다. 중복 요청이나 조회수 상한 초과로 거절된 요청은 큐 항목을 만들지 않는다.

정리는 recordView 요청이 해당 Counter ReentrantLock을 잡은 동안 수행한다. 요청 1회당 같은 게시글의 만료 항목을 최대 100개 처리하며, 큐의 첫 항목이 아직 만료되지 않았으면 그대로 두고 정리를 멈춘다. 큐 항목의 acceptedTick이 현재 Counter의 독자 기록에 남은 acceptedTick과 일치할 때만 삭제한다. 더 최근 조회로 갱신된 stale 항목은 상태를 바꾸지 않는다. 독자별 마지막 인정 시각 조회는 기존 Map.get 기반 중복 판정을 유지한다.

## 이유와 대안

Counter를 유지하면 정리 후에도 기존 누계로 집계를 이어가며 DB 누계 재조회와 객체 수명 경쟁을 줄일 수 있다. 1시간이 지난 독자 기록은 같은 게시글의 요청 경로에서 게시글별 큐로 점진적으로 정리한다. 서버 재시작 시 메모리 상태는 해제된다.

사용이 끝난 Counter까지 퇴거하는 대안은 장시간 실행 중의 메모리 누적을 줄이지만 사용 종료 표시와 재생성·재시도 처리가 필요하다. 이번에는 사용자가 요청한 단순한 구조를 선택하고, Counter 퇴거의 필요성은 실제 메모리 사용량을 측정한 뒤 판단한다. 기존 전역 개수 한도를 유지하는 대안은 새로운 게시글의 집계를 지속적으로 거절할 수 있어 선택하지 않았다. 독자 기록 전역 한도와 용량 초과 오류도 임의 한도로 정상 조회를 거절할 수 있어 선택하지 않았다.

전역 만료 큐를 두는 대안은 다른 게시글 요청으로도 오래된 게시글의 만료 기록을 정리할 수 있지만 별도 큐 클래스와 큐/정리 잠금을 추가한다. 이번 결정은 Counter가 이미 가진 잠금과 소유 상태 안에서 정리해 동시성 경계를 작게 유지한다. 별도 정리 스케줄러를 두는 대안은 요청이 없어도 만료 기록을 줄일 수 있지만 스케줄링 설정, 실행 주기, 서버 시작 시점의 부하를 추가한다. 이번 결정은 HTTP 기록 API와 writer가 아직 없는 단계의 범위를 유지하면서 같은 게시글 recordView 요청에 cleanup 비용을 분산한다.

## 결과와 후속 작업

초기화 등록의 전역 잠금을 없애고 Counter 소유 큐로 만료 독자 기록만 정리한다. HTTP 기록 API, FE 계약, DB writer는 바꾸지 않는다. 기존 post.views.max-counters, post.views.max-viewer-records, 정리 간격 설정은 사용하지 않는다. 별도 scheduler와 @EnableScheduling도 도입하지 않는다. 전역 큐 클래스와 큐/cleanup 전용 잠금도 두지 않는다.

Counter 메모리는 JVM 실행 중 초기화한 게시글 수와 보관 중인 독자 기록·만료 큐 항목 수에 따라 늘어나며 전체 메모리의 절대 상한은 없다. 특정 게시글에 요청이 없으면 그 게시글의 cleanup도 실행되지 않아 cold post의 만료 기록은 유지된다. 요청당 최대 100개 처리 제한은 같은 게시글 backlog 처리를 여러 요청으로 나누지만 전체 backlog를 즉시 비우지는 않는다. 만료 독자 기록 정리는 Counter 객체 수를 줄이지 않는다.

실제 배치 writer·저장 스케줄러·종료 저장은 후속 구현이며, 운영 활성화 전 heap, Counter 수, 독자 기록 수, 게시글별 cleanup backlog 및 저장 지연을 측정한다. 단일 활성 JVM 및 비정상 종료 시 메모리 유실 전제는 유지한다.
