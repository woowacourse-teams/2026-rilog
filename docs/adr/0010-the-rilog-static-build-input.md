# ADR-0010: 더 리로그의 정적 입력과 오전 6시 ISR 갱신

- 상태: 승인
- 날짜: 2026-10-13
- 갱신: 2026-10-14
- 소유자: frontend

## 맥락

더 리로그는 모든 방문자에게 같은 공개 뉴스와 아티클을 제공한다. 최초 빌드에서 정적 HTML을 만들고, 이후 매일 한국 시간 오전 6시에 현재 백엔드 데이터를 받아 더 리로그만 다시 생성한다. 매일 전체 애플리케이션을 빌드하거나 PM2를 재시작할 필요는 없다.

백엔드 API 계약은 현재 응답을 그대로 사용한다. 발행 완료·발행 버전 계약을 추가하지 않으며 개별 게시글의 publishedAt, API의 date, 기사 개수로 발행 완료를 추측하지 않는다. 전날 데이터나 유효한 빈 응답도 현재 API 응답이면 반영한다.

## 결정

1. 메인과 필요한 뉴스 상세를 기존 HTTP 계층으로 읽고 런타임 검증한다. 기사별 링크는 기존 공개 상세 경로를 사용한다.
2. 뉴스 본문의 기존 heading anchor 생성 규칙을 재사용한다. 상세에서 앵커를 생성하는 h1~~h3와 헤드라인을 문서 순서대로 대조하며 개수·제목이 불일치하면 수집을 실패시킨다. h4~~h6 및 접힌 토글 내부처럼 상세 앵커가 없는 제목은 임의 링크를 만들지 않고 검증을 실패시킨다.
3. 공개 데이터와 뉴스 본문을 입력 형식 버전·source·수집 시각·checksum이 있는 JSON으로 고정한다. 이 스냅샷은 백엔드 발행 버전이 아니다. fixture source는 명시적 검증 허용이 필요하다.
4. 입력 준비는 `pnpm prepare:the-rilog`로 명시적으로 실행하고, `pnpm build`는 기존 `next build`를 유지한다. CI는 준비 명령 성공 후 빌드를 실행한다. 명시한 입력이 없거나 손상됐을 때 이전 파일/API/목데이터로 전환하지 않는다. 입력 저장은 임시 파일 완성 후 rename한다.
5. `/the-rilog`는 `force-static`으로 정적 생성하고, 재생성할 때도 서버의 검증된 로컬 스냅샷을 읽는다. 날짜만 작은 Client Component에서 Asia/Seoul 자정·탭 복귀 시 갱신한다. 서버와 첫 클라이언트 렌더는 동일한 자리 표시 상태다.
6. 서버 전용 `THE_RILOG_REVALIDATION_SECRET`의 Bearer 인증을 받은 `POST /api/internal/the-rilog/revalidate`가 현재 API 데이터를 수집한다. 전체 입력 검증과 atomic 저장이 성공한 뒤에만 `revalidatePath('/the-rilog')`를 호출한다. 수집 실패는 기존 스냅샷과 페이지 캐시를 건드리지 않는다. 현재 단일 PM2 프로세스에서는 갱신 중인 추가 요청을 409로 거부하고 완료 후 다음 갱신을 허용한다.
7. 갱신 응답 `202 { checksum, capturedAt }`는 재생성 요청을 접수했다는 의미다. `frontend/scripts/refresh-the-rilog.mjs`가 이어서 loopback `/the-rilog`를 제한 횟수로 요청하고 HTML의 checksum·capturedAt 표시가 둘 다 해당 응답과 일치해야 성공으로 종료한다. 내용이 같은 날도 새 수집 시각까지 확인한다.
8. 갱신 CLI는 재부팅 직후 앱 시작을 기다리기 위해 인증값 없는 GET을 최대 6회 요청한다. 각 요청은 5초, 요청 사이는 1초로 제한하며 준비에 실패하면 수집 POST를 보내지 않는다. 운영 배포가 EC2 systemd timer를 설치한다. timer는 Asia/Seoul 오전 6시마다 갱신 스크립트를 실행하며 `Persistent=true`로 중단 중 놓친 실행을 보충한다. 일일 작업은 전체 빌드·배포·PM2 재시작을 하지 않는다.
9. 배포는 timer를 중단하고 진행 중인 예약 갱신이 끝난 뒤 산출물을 교체한다. 대기 한도를 넘으면 교체 전에 배포를 실패시킨다. 설치 스크립트는 배포 스냅샷과 실제 HTML이 일치하는지 확인한 뒤 timer를 활성화한다. 기존 활성 timer는 배포 종료 시 재시작하므로 실패 후 상태도 확인한다.
10. 수동 준비 workflow는 계속 빌드와 진단용 artifact 생성까지만 수행한다. 운영 갱신 timer와 별개이며 준비 artifact로 운영 배포 완료를 주장하지 않는다.

## 이유와 대안

처음 선택한 빌드 시점 전용 SSG에서 온디맨드 ISR을 허용하도록 변경한다. 기존 입력 검증과 정적 HTML 제공을 유지하면서 콘텐츠 갱신만 전체 빌드에서 분리한다. API 수집을 먼저 끝내고 검증된 스냅샷으로 재생성하면 백엔드 장애나 앵커 오류가 발생했을 때 정상 입력을 덮어쓰지 않는다.

시간 기반 `revalidate = 86400`은 오전 6시에 맞춘 실행을 보장하지 않는다. systemd timer가 갱신 API와 후속 요청을 맡아 첫 방문자를 기다리지 않고 페이지 생성을 확인한다.

## 영향과 검증

- 메인 방문 시 매거진 API를 다시 읽지 않는다. 기존 상세 렌더링·목차·댓글·권한은 유지한다.
- 운영 artifact에는 초기 스냅샷과 갱신 스크립트·timer 설치 파일이 필요하다. `ENV_PROD_FE`에 서버 전용 secret을 넣고 EC2 배포 계정에 설치 스크립트의 `sudo -n` 실행 권한을 준비한다. secret은 artifact나 클라이언트 환경변수에 넣지 않는다.
- 현재 PM2 단일 인스턴스와 로컬 파일시스템 캐시를 전제로 한다. 여러 서버·프로세스로 확장할 때는 입력 저장과 캐시 무효화 공유 방식을 다시 결정한다.
- API 수집 실패는 무효화 이전에 끝나므로 기존 정상 HTML을 보존한다. 저장·무효화 이후 페이지 렌더 실패까지 모든 요청이 이전 HTML로 성공한다고 보장하지 않는다. warm 검증 실패는 성공으로 보고하지 않는다.
- 갱신 실패는 프로세스 종료 코드·systemd journal로 확인하고 애플리케이션 오류는 기존 Sentry 보고 경계를 사용한다.
- 품질 검사는 명시적 fixture snapshot과 테스트 전용 preload를 사용하며 실제 API의 발행 준비 여부를 증명하지 않는다.
- production prerender manifest, 초기 HTML, 브라우저 요청과 메인→상세 앵커 이동을 검증한다. production 서버에서 인증·API 실패 보존·갱신 후 HTML 확인을 별도로 검증한다.

## 운영 적용

구현과 로컬 검증만으로 EC2 timer가 활성화된 것은 아니다. 필요한 secret·서버 권한을 설정한 뒤 운영 배포와 timer 상태·journal을 확인한다. 오전 6시는 수집 시작 시각이며 실제 반영은 수집과 페이지 생성이 끝난 시점이다. 상단 오늘 날짜는 콘텐츠 발행일과 독립적이다.
