# ADR 0007: 게시글 조회수 누계와 배치 기록을 별도 테이블로 관리

- 상태: 승인 (이슈 1 구현 범위)
- 날짜: 2026-10-04
- 소유자: Backend
- 관련 이슈: #694

## 맥락

조회수는 메모리에서 증가분을 모아 배치 저장하는 전략을 사용한다. 이번 이슈는 저장 구조와 발행 시 초기화, 상세 GET의 누계 응답까지 구현한다. 요청별 집계와 배치 실행은 후속 이슈다.

## 결정

- `post_view_count`는 게시글 ID를 PK로 사용하고 누계를 저장한다. `Post` 엔티티에 조회수 필드를 추가하지 않는다.
- `post_view_flush_batch`는 UUID 배치 ID를 PK로 사용하고 게시글 ID, 증가분, 생성 시각을 기록한다. 후속 배치 writer가 이 기록과 누계 증가를 같은 트랜잭션으로 처리한다.
- 두 테이블은 InnoDB와 삭제 cascade가 없는 외래키를 사용한다. 누계는 0..9,007,199,254,740,991, 배치 증가분은 1..9,007,199,254,740,991 범위로 제한한다.
- V4 migration은 모든 기존 PUBLISHED 게시글의 누계를 0으로 초기화한다. 비공개·soft-deleted 게시글도 포함하고 초안은 제외한다.
- 일반 발행과 초안 발행의 기존 트랜잭션 안에서 누계 행을 INSERT한다. 기존 누계를 덮어쓰는 upsert는 사용하지 않는다.
- canonical 상세 GET과 수정용 상세 GET 응답에 숫자형 `viewCount`를 추가한다. GET은 읽기 전용이며 누계를 생성하거나 증가시키지 않는다. 발행된 게시글의 누계 행이 없으면 서버 오류로 드러낸다.

## 이유와 대안

별도 테이블은 게시글 본문 변경 감지와 조회수 쓰기의 소유권을 분리한다. `Post.viewCount` 필드를 두는 대안은 본문 수정 트랜잭션이 조회수 쓰기와 충돌할 수 있어 선택하지 않는다. 배치 PK는 후속 저장 재시도의 중복 적용을 확인할 근거다. 원장 테이블만으로 프로세스 종료 시 메모리 유실을 막지는 않는다.

## 결과와 후속 작업

- 상세 응답에 조회수가 추가되어 기존 필드의 의미와 권한은 유지된다. 엄격하게 미등록 필드를 거부하는 소비자는 별도 호환성 확인이 필요하다. 이 변경에서 FE 파일은 수정하지 않는다.
- 이슈 1 단계에서는 신규 조회를 집계하는 API가 없으므로 신규 누계는 0이다. 이후 메모리 집계·등록 API·멱등 배치 저장을 연결한다.
- migration을 먼저 적용한 뒤 새 backend를 배포한다. V4 적용부터 새 backend 활성화까지 두 발행 경로의 쓰기를 중단해야 한다. 이전 binary는 누계를 생성하지 않으므로 이 구간에 발행이 허용되면 누계 행이 누락된다.
- 이전 binary로 되돌려도 누계·배치 테이블과 기록은 삭제하지 않는다. 이전 binary에서 새 글을 발행했다면 다시 새 backend로 전환하기 전에 쓰기를 중단하고 PUBLISHED 게시글의 누락된 누계 행만 0으로 보충한다. 기존 누계는 덮어쓰지 않는다.
- 원장 보존과 물리 삭제 정책은 후속으로 정한다. 자동 원장 삭제는 이번 범위에 없다.
