# ADR 0017: 이미지 자산과 사용처 참조 관리

- 상태: 승인
- 날짜: 2026-10-27
- 소유자: Backend

## 맥락

한 사용자가 같은 이미지를 여러 게시글이나 임시저장에서 사용하면, 한 사용처를 삭제할 때 기존 태그 처리로 다른 사용처의 이미지까지 정리 대상이 될 수 있다. 이미지의 업로더와 사용처를 별도로 관리해야 한다.

## 결정

- 이미지 업로드 URL 발급 시 원본 객체 키와 업로더를 이미지 자산으로 등록하고, 업로드 태그는 `CONFIRMED`로 지정한다. 일반 파일의 태그 정책은 유지한다.
- 게시글, 임시저장, 사용자 및 블로그 등 이미지 사용처는 자산과 사용처 타입·ID의 참조로 관리한다. 임시저장과 발행된 게시글은 같은 게시글 참조를 사용한다.
- 다른 사용자가 복사한 이미지 URL은 해당 사용자의 참조로 등록하지 않는다. 이 URL을 사용하는 글은 원본 소유자의 이미지 보존을 보장받지 않는다.
- 최초 참조 등록에 따른 `CONFIRMED` 처리 요청을 압축 시작 조건으로 삼는다. 임시저장의 참조도 압축 대상이다. 신규 업로드의 S3 태그가 이미 `CONFIRMED`이므로 태그 값 변경 자체를 압축 트리거로 사용하지 않는다.
- 신규 자산 생성 시점 또는 마지막 참조 제거 시점부터 일주일간 참조가 없으면 삭제 후보로 선정한다. 자산 잠금과 참조 재확인 후 `DELETE_REQUESTED`로 변경하며, 이 상태에서는 새 참조를 거부한다.
- 별도 작업이 삭제 요청 자산을 백업하고 원본과 압축본에 `TEMPORARY` 태그를 적용한다. 성공 후 자산 행을 삭제하고 실패하면 재시도한다. 실제 객체 삭제는 S3 Lifecycle에 맡긴다.

## 이유와 대안

- 소유자 확인만으로는 동일 사용자의 여러 사용처를 구분할 수 없다. 참조 행을 저장하면 각 사용처의 제거와 전체 사용 여부를 확인할 수 있다.
- 태그에 참조 개수를 저장하는 방식은 동시 요청에서 갱신이 충돌할 수 있다. DB 참조와 자산 잠금으로 판단을 직렬화한다.
- 업로드 직후 모든 이미지를 압축하는 방식은 사용하지 않고 버린 이미지까지 처리하므로 선택하지 않는다.

## 결과와 후속 작업

- 첫 단계는 자산·참조 테이블과 이미지 업로드 시 자산 등록만 도입한다. 참조 동기화, 압축 요청, 백업 및 삭제 배치는 후속 작업이다.
- 기존 이미지와 모든 사용처를 백필하고 검증한 후 삭제 배치를 활성화한다. 그 전에는 미사용 `CONFIRMED` 객체가 누적될 수 있다.
- 기존 즉시 `TEMPORARY` 전환 경로는 참조 관리로 대체되기 전까지 동일 이미지 재사용 문제를 해결하지 못한다.
- 외부 저장소 및 DB의 처리 순서, 중복 요청, 실패 재시도와 배포 전환을 후속 구현에서 검증한다. 업로드 API가 반환하는 서명된 태그 헤더는 이미지에 대해 변경된다.
