# ADR-0026: 외부 이미지 가져오기 원본 줄이기와 대기열

- 상태: 제안
- 날짜: 2026-11-10
- 소유자: Backend

## 맥락

외부 이미지 가져오기(ADR 0018, 0021)는 원본 크기 그대로 WebP로 변환하고, 처리 중이면 바로 429 `BUSY`를 돌려준다.

- 1,600만 화소 WebP 한 장의 변환이 약 330MiB를 써서, 압축 변환(ADR 0022)과 겹치면 512MiB 컨테이너가 OOM으로 죽었다.
- 프론트가 여러 장을 동시에 보내면 한 장만 성공하고 나머지는 429로 실패한다. Spring은 429를 그대로 프론트에 전달한다.

근거 실험은 `docs/reports/2026-11-05-image-transform-queue-experiment.md` 9장이다.

## 결정

- 가져오기 변환은 방향 보정 뒤 너비가 2000보다 크면 비율을 유지해 2000으로 줄인다. 작은 이미지는 확대하지 않는다.
  - 2000은 압축본의 가장 큰 너비(`images` 2000)와 같다. 압축본으로 보이는 화질은 바뀌지 않는다.
  - 2000보다 큰 원래 해상도는 저장하지 않는다. 에디터 표시와 압축 실패 시 대체 이미지도 너비 2000 이하가 된다.
- 가져오기는 전용 대기열에서 한 번에 하나씩 변환한다. 압축은 기존 대기열을 따로 쓴다.
  - 대기 최대 10건, 대기 최대 20초. 넘으면 429 `BUSY`(`Retry-After: 2`)다.
  - 다운로드는 대기열 밖에서 한다. 다운로드 중인 요청까지 실행 1건 + 대기 10건을 넘으면 다운로드 전에 429로 거절한다.
  - 기다리는 중 호출자(Spring)가 연결을 끊으면 대기열에서 빼고 변환하지 않는다.
- 이미지 서버 컨테이너에 `MALLOC_ARENA_MAX=2`를 설정한다(Dockerfile). 할당기 기본값에서는 같은 구조의 10분 내구 시험이 21초에 OOM이 났다.
- 대기 20초 = Spring import read-timeout 40초 - 다운로드 상한 10초 - 변환과 S3 업로드 여유. 대기 10건 = 줄인 뒤 한 장 변환 0.3~1.6초 기준으로 20초 안에 끝낼 수 있는 건수.

## 결과

- 실험(512MB, 2 CPU, `MALLOC_ARENA_MAX=2`)에서 혼합·병렬·최악 입력·10분 내구·휴대폰 사진 시나리오 모두 OOM이 없었다. 혼합 시나리오 최고 메모리는 466~496MiB에서 234~315MiB로, 90초 완료 수는 1.3~1.6배가 됐다.
- 10장을 동시에 보내도 429 없이 모두 성공했다(최대 응답 6.9초). 늦게 온 요청은 앞 요청만큼 응답이 늦다.
- Nginx `limit_req`(30r/m, burst 5)가 대기열(10건)보다 먼저 거절할 수 있다. 맞추는 작업은 별도로 한다.
- 대기열은 프로세스 메모리에 있어 재시작·배포 때 기다리던 요청은 연결 끊김으로 실패한다.
- 기존 raw 원본은 바꾸지 않는다.
