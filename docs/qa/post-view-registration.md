# 조회수 활성화 후 연동 QA

관련 이슈: [#753](https://github.com/woowacourse-teams/2026-rilog/issues/753). API 계약은 [조회 등록 API](../../backend/docs/post-view-registration.md), 공개 정책은 [ADR 0012](../adr/0012-post-view-registration-and-visibility.md)를 따른다.

이 문서는 백엔드의 DB 저장 연결과 성능 검증이 끝난 뒤 실제 환경에서 수행할 확인 목록이다. 프론트의 mock 기반 자동화 검증과 구분하며, 아래 항목은 아직 실환경 통과로 판정하지 않았다. POST의 204나 화면의 숫자만으로 DB 영속화를 확인했다고 기록하지 않는다.

## 실행 전 합의

- [ ] 백엔드 담당자와 대상 환경, 적용 버전, DB 저장 주기 및 반영 대기 시간, 집계 활성화 시점을 확인한다. 운영 활성화는 DB writer와 요청 제한 준비가 완료된 뒤 별도로 결정한다.
- [ ] 프론트는 기존 `NEXT_PUBLIC_API_BASE_URL`이 대상 API를 가리키는지 확인한다. 조회수 전용 프론트 env는 추가하지 않는다.
- [ ] 백엔드의 `POST_VIEW_REGISTRATION_ENABLED` 활성화를 확인한다. 이 설정은 백엔드 설정이며 프론트 env에 넣지 않는다.
- [ ] API의 HTTPS 여부와 실제 사이트 관계에 맞는 `POST_VIEW_COOKIE_SECURE`, `POST_VIEW_COOKIE_SAME_SITE`, CORS 허용 origin·credentials 설정을 확인한다. localhost에서 HTTPS 개발 API를 호출하는 cross-site 조건은 `SameSite=None; Secure` 및 실제 브라우저의 쿠키 저장·전송 결과를 함께 확인한다.
- [ ] 공개 개인 글과 팀 글, 작성자·다른 회원·비회원, 팀 OWNER·ADMIN·MEMBER 표본을 준비한다. DB 비교용 글은 다른 방문이 섞이지 않는 개발 표본을 사용한다.

## 등록과 방문 경계

- [ ] 활성화 후 상세 화면을 새로고침하거나 다시 진입한다. 같은 방문에서 비활성 503을 받은 프론트는 자동 재시도하지 않는다.
- [ ] 실제 상세 진입에서만 본문 없는 `POST /v1/posts/{postId}/views`가 발생하고 정상·중복·작성자 방문이 빈 204로 끝나는지 확인한다. 본문 표시는 등록 응답을 기다리지 않아야 한다.
- [ ] 호버·prefetch·SSR의 GET은 조회 등록이나 증가를 만들지 않는지 서버 기록으로 확인한다. 브라우저 Network만으로 서버 요청 부재를 판정하지 않는다.
- [ ] 같은 화면의 재렌더·댓글 query/hash 변경·탭 가시성 변경에서 등록 POST가 중복되지 않는지 확인한다. 다른 글·실제 재진입·문서 새로고침과 브라우저가 지원하는 BFCache 복원은 새 방문 등록을 허용한다.
- [ ] 비회원의 최초 성공 응답이 `rilog_visitor`를 발급하고 다음 요청에서 같은 쿠키를 재사용하는지 확인한다. HttpOnly·Path·수명·Secure·SameSite는 계약과 비교하며 쿠키 원문은 기록하지 않는다. 회원 요청에는 방문자 쿠키를 새로 발급하지 않아야 한다.

## 집계와 영속화

- [ ] 다른 회원과 동일 비회원 식별자의 같은 글 방문이 마지막 인정 시점부터 1시간 내에는 한 번만 반영되는지 확인한다. 거절된 중복 방문으로 인정 시각이 밀리지 않아야 한다.
- [ ] 작성자 본인 방문은 증가하지 않고, 다른 작성자의 글을 방문한 팀 OWNER·ADMIN은 삭제 권한이 있더라도 일반 독자로 집계되는지 확인한다.
- [ ] 합의한 저장 주기 이후 DB 누계와 권한 있는 상세 GET을 비교한다. POST 응답 직후 저장이나 정확히 +1인 화면을 요구하지 않는다. 프론트는 POST 후 상세를 강제 재조회하거나 숫자를 낙관적으로 증가시키지 않는다.
- [ ] 백엔드 담당자가 저장 완료 후의 재시작·복구 결과와 미저장분 처리 기준을 확인하고 증거를 남긴다. 재시작 절차와 다중 인스턴스 집계 지원 여부는 적용된 백엔드 구현 기준으로 확인하며 프론트 검증 결과로 대신하지 않는다.

## 권한·인증·실패

- [ ] 상세 응답의 `viewerPermissions.canDelete=true`일 때만 숫자 조회수와 삭제 버튼을 표시하는지 확인한다. 수정 버튼은 별도의 canEdit 값을 따른다. 조회수 0도 표시되어야 한다.
- [ ] `canDelete=false`이면 상세 응답의 `viewCount`가 명시적 null이고 화면에 조회수가 없는지 확인한다. OWNER·ADMIN·작성자의 예외를 프론트에서 별도로 추정하지 않으며 피드에는 조회수를 추가하지 않는다.
- [ ] A의 상세 응답·삭제 후 재조회가 지연되는 중 로그아웃하거나 B로 전환해도 A의 숫자·권한·삭제 후 이동이 새 세션 화면에 반영되지 않는지 확인한다. 비로그인 수정 진입과 잘못된 수정 URL이 영구 로딩을 만들지 않는지도 확인한다.
- [ ] 같은 세션의 만료 토큰은 한 번 갱신 후 등록을 재시도하고, 정상 갱신으로 로그인 상태나 정상 삭제 후 이동이 깨지지 않는지 확인한다.
- [ ] 이미 본문이 표시된 뒤 조회 등록 POST가 비공개·없는 글의 403·404 또는 기능 비활성 503으로 실패해도 본문을 가리지 않고 같은 방문에서 무한 재시도가 없는지 확인한다. `POST_VIEW_REGISTRATION_DISABLED`인 등록 503만 오류 수집에서 제외되고, 예상하지 못한 5xx·네트워크 오류는 기존 보고 경계를 따르는지 확인한다.
