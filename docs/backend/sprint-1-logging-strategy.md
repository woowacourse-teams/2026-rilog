# 스프린트 1 | 백엔드 로깅 전략

> **많이 기록하는 것이 아니라, 실패의 원인과 대응 대상을 찾을 수 있게 기록한다.**

이 문서는 기존 로깅 체계와 이번 개선의 판단 근거를 정리한다. 대시보드와 알림 구축 결과는 별도 모니터링 문서에서 다룬다.

## 1. 개선 배경

공유된 운영 로그에서는 `REFRESH_TOKEN_MISSING`과 `STATIC_RESOURCE_NOT_FOUND`가 반복됐다. 특히 404 로그에 요청 경로가 없어 **로그는 쌓이지만 어떤 요청이 문제인지 확인하기 어려웠다.**

이에 반복적인 로그는 줄이고, HTTP 예외에는 요청 정보, 외부 연동 실패에는 작업과 대상 정보를 보강했다. 기존 HTTP 상태·오류 코드·응답 본문은 유지했다.

## 2. 수집과 보존

**수집 구조:** 애플리케이션 → 한 줄 JSON stdout → Docker `awslogs` → CloudWatch Logs

SLF4J/Logback과 Spring Boot의 `logstash` 포맷을 사용한다. 문자열 메시지만 검색하지 않고 `event`, `requestId`, `environment` 등 구조화 필드로 조회하기 위해서다. 수집 경로는 Docker 한 곳으로 두어 중복 전송을 피한다.

| 구분 | dev | prod |
| --- | --- | --- |
| 애플리케이션 로그 수준 | DEBUG 이상 | INFO 이상 |
| 출력 형식 | 한 줄 JSON | 한 줄 JSON |
| 로그 그룹 기준 | `/rilog/backend/dev` | `/rilog/backend/prod` |
| 보관 기간 기준 | 7일 | 30일 |

dev는 개발 진단에 필요한 상세 로그를 허용하고, prod는 운영에 필요한 이벤트 중심으로 제한한다. 보관 기간은 dev의 단기 확인과 prod의 장애 회고에 필요한 기간을 구분한 운영 기준이다. SQL·바인딩 값 상세 로그는 두 환경 모두 기본 비활성화한다.

**보관 기간은 AWS 로그 그룹에 설정해야 자동 삭제된다. 위 값은 문서상 기준이며 실제 적용 여부는 별도 확인이 필요하다.** 애플리케이션에 별도 로그 삭제 배치를 두지 않는다. local은 가독성을 위해 일반 콘솔 출력을 유지한다.

## 3. 무엇을 남기고, 무엇을 줄였는가

| 대상 | 현재 정책 | 판단 이유 |
| --- | --- | --- |
| 액세스 토큰 만료·리프레시 토큰 누락 | `shouldLog()`에서 제외. 401 응답 유지 | 정상 갱신·비로그인 흐름에서 반복돼 장애 신호를 가리기 때문. 다른 인증 오류까지 일괄 제외하지 않음 |
| 일반 4xx·리소스 404 | INFO, 스택 제외. `method/path` 추가 | 서버 장애와 구분하되 잘못된 요청 경로는 추적해야 함. 404는 경로별 빈도를 확인한 뒤 추가 제외 여부 판단 |
| 서버 5xx·외부 연동 실패 | 최종 HTTP 예외 핸들러에서 ERROR 1건 | 같은 예외를 서비스와 핸들러에서 중복 기록하지 않고 실제 실패 건수를 구분하기 위함 |
| OAuth 로그인 완료 | 기존 `oauth_login_completed` INFO 유지 | 핵심 인증 흐름의 완료를 확인하기 위함. 개별 외부 호출 성공이나 고정된 `method/path`는 추가하지 않음 |
| Presigned URL 발급 | 실패만 ERROR. 성공 미기록 | 반복 발급 로그를 줄임. URL 발급은 브라우저의 실제 파일 업로드 성공을 의미하지 않음 |
| S3 객체 태깅 | 객체별 최종 SDK 실패만 ERROR. 성공·작업 완료 미기록 | 목적이 전체 성공 이력 수집이 아니라 미해결 태깅 실패 발견이기 때문. 실패 후에도 다음 객체는 계속 처리 |
| 이미지 소유권 불일치·비동기 미처리 예외 | 기존 WARN·ERROR 유지 | 소유권 불일치는 대상 제외 근거로, 미처리 예외는 비동기 작업 이상 징후로 남겨야 함 |

**인증 제외와 S3 성공 미기록은 local/dev/prod 공통 정책이다. DEBUG로 대체하지 않는다.** S3 성공 INFO는 처음 추가했으나, 객체 수에 비례해 증가하는 로그의 활용도가 실패 탐지 목적에 비해 낮아 제거했다.

## 4. 실패 한 건으로 추적할 수 있는 정보

| 질문 | 남기는 정보 |
| --- | --- |
| 어떤 요청인가? | 서버 생성 `requestId`, 응답의 `X-Request-ID`, HTTP `method/path`, `errorCode/httpStatus` |
| 어떤 외부 작업이 실패했나? | `provider`, `operation`, `failureType`, `durationMs`, 취득 가능한 `externalStatus` |
| 어떤 S3 객체를 확인해야 하나? | `bucket`, `key`, 요청한 `tagStatus`, `durationMs`, 취득 가능한 AWS 상태·오류 코드·요청 ID |

- `requestId`를 비동기 작업에도 전달해 원래 HTTP 요청과 S3 실패를 연결한다.
- GitHub는 토큰 교환과 사용자 조회를 구분한다. 외부 응답 상태는 우리 API의 `httpStatus`와 별도로 기록한다.
- Presign 실패는 `http_request_exception`의 `provider=S3`, `operation=presign_put_object`로 조회한다. 별도 중복 이벤트를 만들지 않는다.
- 취득하지 못한 외부 상태·AWS 정보를 추정해서 채우지 않는다. 소요 시간은 숫자로 기록해 비교할 수 있게 한다.

**민감정보는 진단 정보와 분리한다.** 경로에 query string을 포함하지 않고 토큰·쿠키·인증 코드·서명 URL·본문 원문은 기록 대상에서 제외한다. 외부 실패 문맥은 허용된 필드만 출력한다. dev/prod의 스택 출력기는 HTTP 클라이언트 예외와 하위 원인·suppressed 예외의 메시지를 제외하고 예외 종류·스택·취득한 HTTP 상태를 유지한다. 파싱 오류에도 응답 내용이 섞일 수 있기 때문이다. local 일반 콘솔에는 동일한 구조화 스택 마스킹이 적용되지 않는다.

## 5. 발견 이후의 대응과 한계

S3 실패는 **대상 식별 → 현재 DB 참조와 실제 S3 태그 확인 → 필요한 경우 수동 수정 → 재조회 및 처리 기록** 순서로 대응한다. 오래된 실패 로그의 태그를 그대로 재적용하거나, 추가 실패 로그가 없다는 이유로 복구됐다고 판단하지 않는다.

이번 범위는 실패 진단과 수동 대응이며, 애플리케이션 재시도·outbox는 도입하지 않았다. **로그는 복구 큐가 아니다.** 커밋 이후 프로세스 종료나 비동기 작업 유실은 로그 자체가 없을 수 있다. 자동 복구·작업 실행 보장이 필요해지면 영속 작업 저장이나 재조정을 별도로 설계해야 한다.

모니터링 담당자에게는 `s3_object_tagging_failed` ERROR를 알림 연결 대상으로 전달한다. 객체별 진단 로그는 보존하되 알림은 묶어서 중복 통지를 줄이는 방향이다. 실제 알림 연결·팀 수신 여부는 모니터링 문서의 증빙으로 확인한다.

## 6. 구현 검증과 제출 증빙

**코드 검증:** 2026-09-26, `831b1906` 변경 시 전체 894개 테스트와 `./gradlew build`가 통과했다. 인증 로그 제외, HTTP 경로, 외부 실패 문맥·민감정보 제외, S3 성공 무로그·실패 후 후속 처리·요청 ID 연결을 검증했다. 외부 호출은 mock으로 검증했으며, 실제 dev/prod 동작 증빙을 대신하지 않는다.

| 제출 전 첨부할 증빙 | 확인할 내용 |
| --- | --- |
| dev/prod 각각의 CloudWatch 화면 또는 링크 | 환경별 로그 그룹, 실제 보관 기간, 동일 시나리오의 JSON 필드와 `requestId` 조회 결과 |
| 환경별 배포 실행 결과 | [dev 파이프라인](../../.github/workflows/rilog-be-dev.yml), [prod 파이프라인](../../.github/workflows/rilog-be-prod.yml)의 성공 실행 링크 |
| 모니터링 문서 | 핵심 지표 대시보드와 dev/prod 장애 알림의 실제 팀 수신 화면 |
| 장애·성능 문제 1건의 기록 | 발생 시각·증상, 원인, 조치, 조치 뒤 확인한 지표와 로그 |

현재 확인한 것은 **로그 정보 부족과 반복 로그 문제의 개선**이다. 기존 404의 실제 발생 원인이나 장애 해결까지 확인한 것은 아니므로, 스프린트의 장애·성능 문제 사례는 실제 관찰 결과로 별도 작성해야 한다. 트래픽이 적다면 직접 실행한 시나리오의 관찰 결과를 사용한다.
