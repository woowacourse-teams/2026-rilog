# SEO 운영 점검과 기록 양식

이 문서는 #593의 운영 확인 절차다. 코드 검사 결과와 실제 배포 응답을 구분한다. Markdown 응답 수정(#590)과 sitemap 프록시는 `develop`에 반영됐지만, 운영에 반영됐는지는 HTTP 응답으로 확인한다. #592 이미지 대체 텍스트 입력은 이번 SEO 후속 범위에서 제외했다.

## 표본과 확인 순서

1. 점검 날짜·시간(KST), 대상 환경, 배포 식별자(확인 가능할 때), 검사한 URL을 기록한다. 로그인하지 않은 GET으로 확인한다. 캐시가 의심되면 응답 헤더와 재확인 시각을 함께 남긴다.
2. `/feeds`, 공개 개인 블로그와 그 블로그의 발행 게시글, 공개 팀 블로그와 그 블로그의 발행 게시글을 각각 하나 이상 고른다. 피드나 블로그 목록에서 실제 열리는 URL을 선택하고, 글의 공개 상태와 소유 블로그를 확인한다. 삭제·비공개 글을 정상 표본으로 사용하지 않는다. 배포 전후에는 가능하면 같은 URL을 다시 쓴다.
3. `https://rilog.kr/feeds`와 `https://www.rilog.kr/`의 리다이렉트 체인, 최종 URL과 상태를 확인한다. 공개 표본은 최종 `200`, 대표 주소는 `https://www.rilog.kr`을 기대한다. 리다이렉트를 자동으로 따라간 결과만 기록하지 말고 중간 `Location`도 남긴다.
4. 각 최종 응답에서 HTML 원문에 실제 피드 글 목록·블로그 소개/글 목록·게시글 제목과 본문이 포함되는지 확인한다. 브라우저가 실행한 뒤의 DOM만으로 서버 본문을 판정하지 않는다. 스트리밍 HTML은 문서 전체를 읽고 확인한다. `<title>`, description, `rel="canonical"`, meta robots, `X-Robots-Tag`를 기록한다. 공개 페이지의 canonical은 해당 글의 소유 블로그를 포함한 최종 `www` URL이어야 하며, 표본에 `noindex`가 없어야 한다. 검색엔진 색인 여부는 이 응답만으로 판정하지 않는다.
5. `https://www.rilog.kr/robots.txt`의 상태·본문·`Sitemap` 지시를 확인한다. 공개 경로 접근 허용과 비공개 경로 차단은 현재 [`robots.ts`](../../frontend/src/app/robots.ts)를 기준으로 비교한다. `Sitemap` URL은 `https://www.rilog.kr/sitemap.xml`을 기대한다. User-Agent만 바꾼 요청은 실제 검색 봇의 CDN/WAF 통과 증거가 아니다.
6. **운영에서 프론트가 실제 사용하는 API 주소**의 `/v1/sitemap.xml`이 `200`과 XML을 반환하는지 먼저 확인한다. 공개 `api.rilog.kr`의 결과만으로 프론트 설정 값을 단정하지 않는다. 이어 `https://www.rilog.kr/sitemap.xml`의 상태·`Content-Type`·XML 원문을 확인한다. 프론트는 백엔드 XML을 그대로 전달하고 API 오류에는 `503`을 반환한다. XML의 `<loc>`에 `/feeds`, `/about`과 공개 블로그·발행 게시글이 포함되고 호스트가 `www`인지 비교한다. 일부 표본 URL의 부재는 공개 상태·백엔드 수집 조건을 확인한 뒤 결함으로 판정한다.
7. #590 반영이 확인되면 같은 게시글의 `/@{slug}/posts/{id}/markdown`을 GET으로 확인한다. 정상 응답은 `200`, `text/markdown`, 게시글 HTML URL을 가리키는 `Link: <…>; rel="canonical"`, `X-Robots-Tag: noindex`, 제목·canonical을 포함한 frontmatter와 본문을 기대한다. ID `0`은 `404`를 기대한다. 운영 API를 인위적으로 중단하지 않는다. API 장애·시간 초과·잘못된 응답의 `503` 계약은 [Markdown 단위 테스트](<../../frontend/src/app/(with-sidebar)/(with-footer)/[slug]/posts/[postId]/markdown/route.unit.test.ts>)를 참조한다.
8. Search Console의 `sc-domain:rilog.kr`에서 제출된 sitemap URL·처리 상태·마지막 읽기·발견된 URL 수, 페이지 색인 제외 사유와 대표 URL Inspection, 검색 실적의 기간·노출·클릭을 확인한다. **보고서의 갱신 기준일을 배포 시각과 별도로 기록한다.** 색인 반영은 지연될 수 있으므로 배포 직후 색인 수 증가를 통과 조건으로 삼지 않는다. sitemap 제출과 색인 재요청은 이 읽기 점검에서 하지 않는다.

HTTP 확인에는 `curl -sS -D headers.txt -o page.html 'https://www.rilog.kr/feeds'`처럼 헤더와 **GET 본문**을 함께 보관할 수 있다. 리다이렉트 확인에는 먼저 `-L` 없이 요청하고, 최종 본문 확인 시 별도로 `-L`을 사용한다. HTML·XML 해석은 저장한 원문에서 확인하며 `curl -I`의 HEAD 결과만으로 본문을 판정하지 않는다. 경로와 호스트가 다른 표본은 URL을 바꿔 같은 순서로 검사한다.

## 배포 전 기준: 2026-09-27 00:36~00:44 KST

이 시각에 확인한 공개 표본은 다음과 같다. 모두 `200`이고 서버 HTML에 실제 콘텐츠가 있었지만 canonical은 `https://rilog.kr`(apex)을 가리켰다.

| 공개 URL                                  | 서버 본문                      | 당시 canonical                        |
| ----------------------------------------- | ------------------------------ | ------------------------------------- |
| `https://www.rilog.kr/feeds`              | 글 카드·게시글 링크            | `https://rilog.kr/feeds`              |
| `https://www.rilog.kr/@gustn99`           | 개인 블로그 프로필·게시글 목록 | `https://rilog.kr/@gustn99`           |
| `https://www.rilog.kr/@harudle`           | 팀 소개·게시글 목록            | `https://rilog.kr/@harudle`           |
| `https://www.rilog.kr/@gustn99/posts/120` | 게시글 제목·작성자·게시일·본문 | `https://rilog.kr/@gustn99/posts/120` |
| `https://www.rilog.kr/@harudle/posts/123` | 게시글 제목·작성자·게시일·본문 | `https://rilog.kr/@harudle/posts/123` |

Apex `/feeds`는 `www`로 `301` 이동했다. robots의 sitemap 지시도 apex였다. 프론트 sitemap은 `200` XML이었지만 `<loc>`은 apex의 `/feeds`와 `/about` 두 개뿐이었다. 공개 `https://api.rilog.kr/v1/sitemap.xml`은 `404`였다. 이 결과는 **당시 운영 응답**이며 현재 배포 상태나 프론트의 실제 API 설정을 증명하지 않는다.

배포 후 우선 확인할 관측은 다음과 같다. 실제 색인 피해나 원인은 아직 확인하지 않았다.

| 당시 관측                                                                 | 확인할 영향과 담당 경계                                       | 배포 후 확인                                                             |
| ------------------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 최종 `www` 주소와 canonical·robots의 apex 주소가 불일치                   | 대표 주소 신호 충돌 여부. FE 배포·사이트 URL 설정·호스트 운영 | 공개 표본, robots, sitemap의 호스트가 `www`로 일치하는지 확인            |
| sitemap에 공개 블로그·게시글이 없고 공개 API 주소에서 XML 대신 `404` 응답 | URL 발견 경로의 범위. BE sitemap 배포·FE API 설정/프록시      | 실제 운영 API의 XML 응답을 먼저 확인하고 FE 원문 전달·공개 URL 목록 확인 |

위 관측만으로 색인 제외 원인이나 실제 Googlebot 접근 차단을 확정하지 않는다. Search Console의 비공개 수치·화면 자료·URL Inspection 결과는 접근 제한된 증거 위치에 보관하고 공개 저장소에는 필요한 판정과 비공개 자료의 위치/접근 방법만 기록한다.

## 배포 전후 점검 기록 양식

아래 양식을 배포 전과 배포 후에 각각 복사해 채운다. 판정은 `통과`, `결함 확인`, `배포 대기`, `접근·도구 제한으로 미검증` 중 하나를 사용한다. 관측하지 않은 항목을 통과로 표시하지 않는다.

| 단계·시각(KST)                | 환경·배포 식별자        | URL 또는 Search Console 항목 | 실제 상태·본문·헤더/보고서 기준일 | 기대 결과          | 판정                                               | 증거 위치·미검증 사유                     |
| ----------------------------- | ----------------------- | ---------------------------- | --------------------------------- | ------------------ | -------------------------------------------------- | ----------------------------------------- |
| 배포 전/후 · YYYY-MM-DD HH:mm | production · SHA/미확인 | URL 또는 항목                | 상태·최종 URL·본문/metadata 요약  | 기대 상태·URL·지시 | 통과/결함 확인/배포 대기/접근·도구 제한으로 미검증 | 공개 HTTP 원문 경로 또는 비공개 증거 위치 |

결함은 아래 표로 정리한다. 확인된 사실과 원인 추정은 분리하고, 미검증이면 필요한 확인 방법을 다음 조치에 적는다.

| 우선순위 | 확인된 결함·재현 URL         | 사용자·검색 접근 영향 | 담당 경계          | 다음 조치                       | 상태·증거           |
| -------- | ---------------------------- | --------------------- | ------------------ | ------------------------------- | ------------------- |
| P1/P2/P3 | 실제 응답과 기대 결과의 차이 | 영향 범위와 근거      | FE/BE/배포·CDN/WAF | 담당자가 확인하거나 수정할 항목 | 확인 시각·증거 위치 |

#593은 운영 배포 후 이 기록과 Search Console에서 확인한 범위, 접근·도구 제한으로 남은 항목을 채운 뒤 마무리한다. 운영 확인 중 코드 결함이 발견되면 해당 소유 파트의 기존 하네스에서 가장 낮은 적절한 계층으로 회귀를 보호한다. 새 E2E는 브라우저에서만 재현되는 구체적인 사용자 피해가 확인될 때 검토한다.
