# 방문 기록 Caffeine 전환 설계

- 상태: 승인된 계획에 따라 구현·검증 완료. 실행 결과는 연결된 구현 계획에 기록했다.
- 대상: 현재 `be/feature/#697-게시글-조회수-메모리-집계-및-1시간-중복-제한-구현` 브랜치.
- 근거: 현재 대화의 권장안, `backend/docs/post-view-memory-counter.md`, ADR 0008, 실험 브랜치의 Caffeine 계약 테스트와 k6 결과.

## 목표

방문 기록의 보관과 만료를 Caffeine에 맡기고, 조회수 집계·동시성·배치 상태 관리는 기존 Counter에 유지한다. 방문 기록만 교체하는 `ViewerRecordStore`와 집계 구현 전체를 교체하는 `PostViewStore`를 보존한다.

## 결정

1. **동시성:** `PostViewCounter`의 게시글별 `ReentrantLock`을 유지한다. 중복 확인·방문 기록 저장·증가·현재 값 읽기·배치 상태 전환을 같은 락으로 보호한다. Caffeine `compute()` 기반 동기화로 변경하지 않는다.
2. **방문 기록:** 게시글별 `CaffeineViewerRecordStore`를 생성한다. `Cache<ViewerIdentity, Long>`에 마지막 인정 tick을 저장하고 `expireAfterWrite(ViewPolicy.DUPLICATE_WINDOW)`와 주입된 ticker를 사용한다.
3. **중복 정책:** 마지막 인정 이후 1시간 미만은 거절하고, 정확히 1시간부터 다시 인정한다. 거절한 중복 요청은 기록을 갱신하지 않는다. 회원 ID와 익명 UUID를 같은 사람으로 합치지 않는다.
4. **만료:** 방문 기록은 논리적으로 만료되면 조회에서 없는 것으로 처리한다. 물리적 삭제가 정확히 1시간에 완료된다고 보장하지 않는다. 별도 정리 스케줄러와 Caffeine scheduler는 도입하지 않는다.
5. **메모리:** Counter 제거와 임의의 `maximumSize`를 도입하지 않는다. 중복 판정에 필요한 유효 기록을 용량 정책으로 먼저 제거하지 않는다. 전체 메모리 상한을 보장하는 설계는 아니다.
6. **집계 상태:** 현재 조회수는 `confirmedCount + pendingDelta + inFlightBatch.delta()`다. 배치 준비 시 대기분을 이동하고, DB 반영 확인 후 해당 배치만 확정한다. 실패·결과 불명확 상태는 같은 배치를 유지한다.
7. **조립:** 기존 Registry의 factory 생성자로 Caffeine 구현을 전달한다. 기존 기본 생성자와 Queue 구현은 비교·회귀 검증용으로 유지한다. Spring에서 사용할 구현은 `PostViewConfig`에서 명시한다.
8. **교체 경계:** 상위 서비스와 후속 writer는 `PostViewStore`에 의존한다. Redis 전환은 이 계약의 별도 구현으로 하며 저장·원자성·배치 상태를 함께 옮긴다. 이번에는 Redis 구현체를 만들지 않는다.

## 파일과 의존성

- 실험 브랜치에서 `CaffeineViewerRecordStore.java`와 계약 테스트만 선별적으로 가져온다. benchmark API, Gradle benchmark source set, 결과 파일 전체를 병합하지 않는다.
- Caffeine 의존성은 Spring Boot BOM 관리 버전을 사용한다. 실험에서 해석된 버전은 3.2.4이며, 전환 시 실제 해석 버전을 다시 기록한다.
- Java 21과 기존 Spring Boot·DB·검증 도구를 유지한다. Spring Cache 어노테이션 계층은 추가하지 않는다.
- 기존 인터페이스·Counter·Registry 초기화 공유 및 실패 복구 동작을 유지한다. DB 초기화 I/O를 Counter 락이나 Map 원자적 연산 안으로 이동하지 않는다.

## 완료 조건

- Spring 기본 조립이 Caffeine 방문 기록 구현을 선택한다.
- Queue와 Caffeine 모두 1시간 경계, 중복 요청으로 만료 미연장, 같은 독자 동시 요청, 다른 독자 동시 요청, 배치 합계 보존, tick 순환, 상한 거절 시 기록 미갱신 계약을 만족한다.
- `PostViewStore`만 사용하는 테스트에서 배치 재반환·중복 완료·저장 중 새 조회·실패 후 재시도를 검증한다.
- 기존 Queue 전용 정리량·stale 기록 테스트를 유지한다. 테스트 목적으로 Counter나 캐시를 공개 API에 노출하지 않는다.
- 기존 H2·MySQL·build 검증 결과와 실행하지 못한 항목을 기록한다.

## 범위와 후속 작업

이번 범위는 집계 엔진의 방문 기록 구현 전환이다. 프론트엔드, 공개 HTTP 계약, 인증 쿠키, 상세·피드 연결, 실제 DB batch writer, 저장 스케줄러, 종료 저장은 변경하지 않는다.

운영에서 조회수가 증가하려면 별도 후속 작업으로 조회 등록 POST와 방문자 해석, 권한 검증, 상세·피드의 메모리 누계 조회, 배치 원장과 증가 UPDATE의 동일 트랜잭션, 재시도·종료 저장을 구현해야 한다. 이 전환 완료만으로 운영 기능이 완성되는 것은 아니다.

## 운영 POST 연결 전 요청 제한

사용자가 대량 봇 요청 가능성을 추가로 제기했다. 한 시간 중복 제한은 조회수 인정 정책이며 HTTP 요청 처리량이나 메모리 사용량의 상한이 아니다. 같은 방문자의 반복 요청도 CPU와 네트워크를 사용하고, 방문자 ID를 바꾼 요청은 새 기록을 계속 만들 수 있다.

조회 등록 POST를 운영에 연결하기 전에 모든 API에 적용하는 공통 rate limiter가 이 경로도 보호하도록 입구에서 요청 속도를 제한한다. 조회수 전용 limiter를 중복 구현하지 않고 필요한 정책을 설정한다. 계정·방문자별 제한, 공유 IP를 고려한 보조 IP 제한, 전체 요청 속도 및 동시 처리량을 조합하며 기존 인프라와 정상 요청 분포를 확인한 뒤 수치를 정한다. 초과 요청은 집계 전에 거절하고 429 등 기존 오류 계약과 호환되는 응답을 설계한다. 분산 IP·새 쿠키 요청은 식별자별 제한만으로 막을 수 없으므로 전체 처리량 보호도 검증한다.

Caffeine `maximumSize`로 중복 기록을 임의 퇴거시키는 것을 요청 제한의 대체로 사용하지 않는다. 유효 기록이 제거되면 같은 독자를 다시 인정할 수 있다. 이번 전환에는 수치가 정해지지 않은 limiter나 새 의존성을 추가하지 않고, 후속 API 구현의 필수 작업·검증 항목으로 포함한다.

## 판단 근거와 한계

실험한 Queue·Caffeine 두 버전은 모두 Counter의 동일한 락과 배치 상태를 사용했다. 일반 조회에서 보편적인 성능 우위는 확인하지 못했고, 만료된 기록 10만 개 조건에서는 Caffeine의 요청 지연이 더 작았다. 초기 기록 10만 개의 유지 힙은 Caffeine이 약 0.53~2.23 MiB 더 사용했다.

이는 로컬 테스트 API와 같은 머신의 k6를 사용한 결과다. 실제 DB writer·인증·운영 API, `compute()` 전환의 성능, 장시간 운영의 메모리 상한은 검증하지 않았다. 단일 활성 JVM과 비정상 종료 시 미저장 증가분·방문 기록 유실 전제는 유지한다.
